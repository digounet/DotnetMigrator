Migrator: aplicações .NET Framework na AWS

Lê a aplicação inteira e gera, ao lado da original, um repositório pronto para a esteira da plataforma: código em app/src, infraestrutura em CloudFormation com parâmetros por ambiente (dev, hom, prod), descritor da esteira e testes de aceitação. O padrão é lift-and-shift: código intocado em .NET Framework 4.8.1 rodando em EC2 Windows, com URLs e e-mails fixos virando parâmetros e senhas virando referências ao Secrets Manager. Com --target net10, reescreve o código para .NET 10, compila, testa e hospeda em ECS Fargate. Em qualquer caso entrega o inventário, os bancos, tabelas e campos acessados, as sugestões de modernização e a arquitetura alvo.

Pensado para migrar um portfólio, não um projeto

Dezenas de aplicações com a mesma esteira, a mesma arquitetura de referência e um inventário comparável entre elas. O código original nunca é alterado: a saída é uma cópia ao lado, no layout do repositório da plataforma.

Lift-and-shift (padrão)

Sai do datacenter sem reescrever

Projetos elevados para .NET Framework 4.8.1 com o código como está. URLs e e-mails fixos no código e nos configs viram parâmetros com um valor por ambiente; senhas, tokens e connection strings viram nomes no Secrets Manager, com os valores em _secrets/ fora do git. EC2 Windows com IIS, Auto Scaling, ALB e CodeDeploy em CloudFormation.

Modernização (--target net10)

Converte, compila e prova

csproj → SDK-style, packages.config → PackageReference verificado no feed, web.config → appsettings.json, Program.cs gerado, controllers Web API reescritos com Roslyn, Windows Service → Worker Service, IConfiguration injetado. Depois: build por projeto, testes migrados executados e /health probado. ECS Fargate; Lambda só com --serverless. Soluções mistas (.NET Framework + .NET 6/8 + netstandard) são tratadas inteiras: os projetos já modernos têm o appsettings.json e o código analisados do mesmo jeito.

Análise

Aponta os gaps e os dados

AutoMapper 15+, MediatR 13+, FluentAssertions 8+, EPPlus 5+, MassTransit 9+ (viraram pagos), EWS, Topshelf, Crystal (descontinuados) e C# que compila mas muda no .NET 10/Linux: code pages, cultura, TransactionScope, DateTime.Now em UTC, caminhos com barra invertida. E, sempre, os bancos, tabelas e campos que o código acessa, com tecnologia, operação e arquivo:linha. As DLLs locais são inspecionadas tipo a tipo: API removida do .NET 10 é bloqueante, Registro/P/Invoke/Event Log viram dependência Windows na hospedagem.

Infra no layout da plataforma

Pronto para a esteira, com o guia de implantação

infra/service.yml fiel ao da plataforma (NLB, Datadog/FireLens, tags finops, roles via SSM), infra/data.yml, infra/{dev,hom,prod}/parameters.json, scripts do CodeDeploy, .iupipes.yml, specs TAAC e workflow. O relatório e o README da saída trazem o guia de implantação: o que roda onde, cada parâmetro por ambiente, bancos, segredos, variáveis, filas, rede, esteira e checklist. Tudo passa no cfn-lint; Terraform com --iac terraform.

Portfólio e LLM

Dezenas de apps, um plano

portfolio analisa todas as soluções de uma pasta e consolida ranking de esforço, gaps mais frequentes, bancos compartilhados e ondas de migração, comparável a uma baseline. Com --llm api (LLM corporativa via API, só client_id e client_secret) ou --llm ollama, o modelo fecha o build (revertido se piorar), rascunha conversões e tria falsos positivos. Sem LLM, tudo continua funcionando.

Como funciona

analyze roda tudo em memória e só grava os relatórios; migrate também grava o repositório e, no destino .NET 10, compila e testa. O diagrama mostra o pipeline de modernização; no lift-and-shift as etapas de reescrita e build são puladas e o restante (perfil, dados, modernização, arquitetura, infra) é igual. O que a LLM acrescenta

Tudo que é determinístico continua determinístico. A LLM entra onde regra não alcança: entender intenção e gerar código novo.

  • Correção do build: arquivo com erro + erros + dicas → versão corrigida → recompila. Se não reduzir erros, reverte e tenta de novo com o feedback do compilador. Nunca deixa o arquivo pior que o original.
  • Rascunhos: IHttpModule → middleware, filtros do System.Web → IActionFilter, ServiceBase → BackgroundService, salvos como .Migrator.cs.txt.
  • Leitura do arquiteto: resumo executivo, decisões por projeto, riscos prioritários e ordem de trabalho a partir do dossiê estruturado.

A LLM corporativa entra com --llm api: a URL do gateway é fixa no código e só MIGRATOR_LLM_CLIENT_ID e MIGRATOR_LLM_CLIENT_SECRET precisam ser informados (OAuth2 client credentials, corpo compatível com OpenAI, modelo por parâmetro). Outros provedores implementam ILlmAssistant (systemMessage + userMessage → texto). Respostas são cacheadas; o Ollama local serve para desenvolvimento.

Início rápido

git clone https://github.com/digounet/DotnetMigrator.git
cd DotnetMigrator
dotnet build Migrator.slnx

# 1) só análise: inventário, dados acessados, modernização e arquitetura, sem gravar código
dotnet run --project src/Migrator.Cli -- analyze C:\src\MinhaApp\MinhaApp.sln

# 2) lift-and-shift (padrão): gera C:\src\MinhaApp.net481 no layout da plataforma (app/src, infra/, .iupipes.yml, tests/)
dotnet run --project src/Migrator.Cli -- migrate C:\src\MinhaApp\MinhaApp.sln

# 3) modernização: gera C:\src\MinhaApp.net10 com Dockerfiles, compila, testa e gera a infra ECS
dotnet run --project src/Migrator.Cli -- migrate C:\src\MinhaApp\MinhaApp.sln --target net10

# 4) portfólio: todas as soluções de uma pasta, ranking de esforço e ondas
dotnet run --project src/Migrator.Cli -- portfolio C:\src\aplicacoes --report C:\src\portfolio

# 5) com a LLM corporativa fechando o build (ou --llm ollama para um modelo local)
$env:MIGRATOR_LLM_CLIENT_ID = "..."; $env:MIGRATOR_LLM_CLIENT_SECRET = "..."
dotnet run --project src/Migrator.Cli -- migrate C:\src\MinhaApp\MinhaApp.sln --target net10 --llm api

Como estender

As regras são dados em src/Migrator.Core/Data/: um pacote novo é uma linha em PackageRules ou ModernizationRules; um padrão de código é uma regex em CodeRules ou CodeModernizationRules; um sinal de arquitetura entra no enum Signal do ApplicationProfiler e é usado pelo AwsArchitect. O README traz exemplos de cada um e o passo a passo para plugar uma nova LLM.
