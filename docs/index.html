Migrator: do .NET Framework ao .NET 10 na AWS

Lê a aplicação inteira, gera uma cópia migrada e compila, executa os testes e sobe a app para testar /health. Entende o que a aplicação faz, aponta bibliotecas que viraram pagas ou foram descontinuadas e código que muda de comportamento no Linux, e propõe onde cada projeto deve rodar na AWS, com Dockerfile, Terraform e pipeline prontos. Em lote, consolida dezenas de aplicações em ondas de migração. Com uma LLM plugada, ainda fecha o build sozinho.

Pensado para migrar um portfólio, não um projeto

Dezenas de aplicações com o mesmo pipeline, a mesma arquitetura de referência e um inventário comparável entre elas. O código original nunca é alterado: a saída é uma cópia ao lado.

Migração

Converte, compila e prova

csproj → SDK-style, packages.config → PackageReference verificado no nuget.org, web.config → appsettings.json com credenciais movidas para _secrets/, Program.cs gerado, controllers Web API reescritos com Roslyn, Windows Service → Worker Service, IConfiguration injetado. Depois: build por projeto, testes migrados executados e /health probado.

Modernização

Aponta os gaps

AutoMapper 15+, MediatR 13+, FluentAssertions 8+, EPPlus 5+, MassTransit 9+ (viraram pagos), EWS, Topshelf, Crystal (descontinuados) e C# que compila mas muda no .NET 10/Linux: code pages, cultura, TransactionScope, DateTime.Now em UTC, caminhos com barra invertida.

Arquitetura AWS

Recomenda e gera a infraestrutura

ECS Fargate para web, Lambda para automações orientadas a evento (com Function.cs gerado), tarefa agendada para jobs, containers Windows só com dependência dura. Sai como módulo Terraform validado (VPC, ECS/ALB, RDS, S3, SQS, SES, ElastiCache, IAM, alarmes) e workflow de deploy no GitHub Actions.

Portfólio e LLM

Dezenas de apps, um plano

portfolio analisa todas as soluções de uma pasta e consolida ranking de esforço, gaps mais frequentes, bancos compartilhados e ondas de migração, comparável a uma baseline. Com --llm, o modelo fecha o build (revertido se piorar), rascunha conversões e tria falsos positivos. Sem LLM, tudo continua funcionando.

Como funciona

analyze roda tudo em memória e só grava os relatórios; migrate também grava a cópia, compila, testa e gera os artefatos de deploy. Diagrama interativo: clique nos nós, use as visões guiadas e o zoom.

O que a LLM acrescenta

Tudo que é determinístico continua determinístico. A LLM entra onde regra não alcança: entender intenção e gerar código novo.

  • Correção do build: arquivo com erro + erros + dicas → versão corrigida → recompila. Se não reduzir erros, reverte e tenta de novo com o feedback do compilador. Nunca deixa o arquivo pior que o original.
  • Rascunhos: IHttpModule → middleware, filtros do System.Web → IActionFilter, ServiceBase → BackgroundService, salvos como .Migrator.cs.txt.
  • Leitura do arquiteto: resumo executivo, decisões por projeto, riscos prioritários e ordem de trabalho a partir do dossiê estruturado.

A interface é mínima (systemMessage + userMessage → texto): basta implementar ILlmAssistant sobre o SDK da empresa, OpenAI, Bedrock ou Gemini. Respostas são cacheadas; o Ollama local serve para desenvolvimento.

Início rápido

git clone https://github.com/digounet/DotnetMigrator.git
cd DotnetMigrator
dotnet build Migrator.slnx

# 1) só análise: inventário, modernização e arquitetura, sem gravar código
dotnet run --project src/Migrator.Cli -- analyze C:\src\MinhaApp\MinhaApp.sln

# 2) migração: gera C:\src\MinhaApp.net10 com Dockerfiles, compila e gera relatórios
dotnet run --project src/Migrator.Cli -- migrate C:\src\MinhaApp\MinhaApp.sln

# 3) portfólio: todas as soluções de uma pasta, ranking de esforço e ondas
dotnet run --project src/Migrator.Cli -- portfolio C:\src\aplicacoes --report C:\src\portfolio

# 4) com LLM local (Ollama) fechando o build
ollama pull qwen2.5-coder:7b
dotnet run --project src/Migrator.Cli -- migrate C:\src\MinhaApp\MinhaApp.sln --llm ollama --llm-model qwen2.5-coder:7b

Saídas: migration-report.html (navegável), migration-report.md (para PR/wiki, com o diagrama), inventory.xlsx (abas Resumo, Inventário, Modernização, Arquitetura AWS), inventory.csv, modernization.csv, migration-result.json e build-verification.log. Na cópia migrada: Dockerfile por projeto, infra/terraform, .github/workflows/deploy.yml e _secrets/ (fora do git e do Docker).

Como estender

As regras são dados em src/Migrator.Core/Data/: um pacote novo é uma linha em PackageRules ou ModernizationRules; um padrão de código é uma regex em CodeRules ou CodeModernizationRules; um sinal de arquitetura entra no enum Signal do ApplicationProfiler e é usado pelo AwsArchitect. O README traz exemplos de cada um e o passo a passo para plugar uma nova LLM.
